# 实验日志：从 79% 到 94.6% 的过程

> 这份日志记录**每一次尝试的结果，包括失败的**。
> 结论优先看 [§8 一页总结](#8-一页总结)，过程看各节。

---

## 0. 起点：一个需要被质疑的数字

v1 的结果是「模型原始 79.77% → 规则纠偏 + 人工复核后 **98.09%**」。

这个数字在文档里标了 in-sample，但它有个根本问题：

- 48 条规则是在**同一批 262 条**上反复迭代出来的
- 换一批视频，规则大部分失效
- 模型本身的泛化水平只有 ~80%

**所以 v3 之后所有改动都遵循一条规则：必须在没见过的数据上验证，否则不采纳。**

这条规则最终拦下了 5 个看起来能涨、实际无效的改动。

## 1. 先修数据，再谈模型

新表（`工作簿1.xlsx`，646 条 / 6 游戏 / 4 平台）的结构和旧表完全不同。
读数据就踩了三个坑：

| 坑 | 表现 | 处理 |
|---|---|---|
| **重复列名** | `1月快手-暗区突围` 有两个「视频类型」列（idx 3 是标签，idx 12 是「视频」形式） | 按下标定位，不按列名 |
| **标签列不是标签** | `暗区` 表的「作品分类」是 `游戏-射击游戏` 这类游戏品类 | 改从「内容精炼（人工)」的 `类型：描述` 前缀解析 |
| **异常标签** | dnfm 有 12 条标签是 `/`，另有「游戏实况与剪辑」这类合并口径 | 归一化 + 标记为无真值 |

反过来，v4 的四个 B站 表列数完全不同（17 / 19 / 26 / 26 列），**必须按列名定位**。
所以两个 prepare 脚本一个用下标、一个用列名——原因写在各自文件头。

### 顺带修掉 3 个潜伏的 bug

v2 的数据里没有「无真值行」，所以这些问题一直没暴露：

| 文件 | 问题 | 影响 |
|---|---|---|
| `evaluate_v2.py` | 只过滤了无预测、没过滤无真值 | 94 条无标签样本被当成全错，准确率从 **66.85% 被压到 57.03%** |
| `text_prior.py` | 把 `""` 当成一个类别参与训练（空类是第三大类） | 文本先验 top1 虚高到 **62.54%**，修正后 59.24% |
| `context.py` | 检索语料没过滤空标签 | 话题/作者/时长先验被污染 |

## 2. 第一次「异常好的结果」：标签泄漏

给 `暗区` 表补标签后跑了一遍，结果好得可疑：

| | 补标签前 | 补标签后 |
|---|---:|---:|
| 暗区准确率 | 52.4% | **75.6%** |
| 宽口径样本通过率 | 15.4% | **59.0%** |

**跳得太漂亮，去查了送的 context**：

```
相似作品参考：
- 描述：...#暗区突围PC 游戏宣传：11.20国服测试下载开启 → 标签：游戏宣传
```

原因：我把「内容精炼（人工)」整段拼进了 `desc` 作为辅助信息，
而它**首行就是 `游戏宣传：`——标签本身**。加上暗区样本进入检索语料后，
相似示例直接展示了「标签 → 标签」的对应关系。**模型只需做字符串匹配。**

修复：`strip_anqu_prefix()` 剥掉首行类型前缀，保留正文。

| 版本 | 整体 | 暗区 | 宽口径 39 条 | 文本先验 top1 |
|---|---:|---:|---:|---:|
| 泄漏版 | 68.17% | 75.6% | 58.97% | 61.36% |
| **修复后** | **64.01%** | **59.8%** | **35.90%** | **59.94%** |

修复后全量 646 条里 `desc` 含「真值标签：」的泄漏为 **0 条**。

> **经验**：结果异常好时，第一件事是查有没有把答案漏进去。

## 3. 引入「业务口径」：承认标注本身有分歧

严格比对标签会严重低估实际可用性。原因是很多内容**天然横跨两类**：

> 「吐槽游戏机制 + 给出规避技巧」——是游戏吐槽还是游戏攻略？
> 「单局内玩梗 + 连续讲解」——是游戏实况、实况解说还是创意整活？

标注员按主观侧重打标，模型按自己的判定顺序打标，两者都自洽。

做法：把这类标签对标为「业务上可互换」，两种判法都算对。

| 数据集 | 严格 | 业务口径 | 提升 |
|---|---:|---:|---:|
| v3（抖音/快手，446 条） | 59.6% | **74.2%** | +14.6pp |

**这一步没有改任何模型行为**，只是承认了标注本身的模糊性。

## 4. 规则层：话题 + 作者（唯一稳定有效的优化）

### 做法

从作品元数据（话题标签、作者名）挖掘高纯度规则，**只读描述与作者、不读真值**。
在 dev（70%）挖掘，test（30%）验证。

### 阈值怎么定的

跑了 10 个随机划分，对比不同阈值：

| 规则源 | 阈值 | test 平均提升 | 正收益种子 | 最差 |
|---|---|---:|---:|---:|
| 仅话题 | ≥5 | +1.89pp | 7/7 | +2 |
| 仅作者 | ≥5 | +1.26pp | 7/7 | +1 |
| 话题+作者 | ≥3 | +3.09pp | 10/10 | +1 |
| **话题+作者** | **≥4** | **+2.57pp** | **10/10** | **+2** |
| 话题+作者 | ≥5 | +2.06pp | 10/10 | +1 |
| 话题+作者 | ≥6 | +1.54pp | 9/10 | 0 |

**选了 ≥4 而不是均值最高的 ≥3**：≥3 的最差种子只有 +1，且 dev/test 差距 0.97pp；
≥4 最差 +2，差距 0.72pp。**下界更好、过拟合更少，更适合上生产。**

### 效果

v3：**76.68% → 78.03%**（+1.35pp，改动 15 条：修复 12，打坏 3）

挖出的规则长这样：

| 规则 | dev 覆盖 |
|---|---|
| `#暗区突围S16宿命之战` → 创意整活 | 16/16 |
| `@暗区突围 小船子` → 创意整活 | 7/7 |
| `@崎七怪怪` → 二创类 | 6/6 |
| `@HangHang` → 高光剪辑 | 6/6 |
| `#FPS` / `#地图设计` → 游戏宣传 | 6/6、5/5 |

注意 `幻术（光明神）` 没有进规则——他 32 条内容散成 5 类，纯度不达标，
被阈值自动挡掉了。**不需要人工判断，纯度门槛替我们做了决定。**

## 5. 按表分治：发现「不同工作表口径相反」

### 起因：一次失败的提示词实验

观察到「创意整活」与「游戏实况」的混淆最多，且模型的判断依据里写着：

> 根据判定规程，单局游戏过程中发生的搞笑、脑洞、玩家互动、意外事件，**一律算游戏实况**

而此时话题先验是 `#暗区出金联盟 → 创意整活 100%`、文本模型 0.61、相似示例全是创意整活。
**先验全给对了，模型因为规程语气太硬而拒绝采纳。**

于是写 v9：把判别点从「是否单局」改成「核心看点是不是梗」。

先在 186 条「错误密集」子集做 A/B：严格 +14.1pp，净 **+7**，看起来可用。

**全量重跑是 −14。**

| 工作表 | v8 | v9 | 变化 |
|---|---:|---:|---:|
| 1月快手-暗区突围（62 条全标创意整活） | 86.7% | 95.0% | **+8.3pp** |
| 2月抖音-地铁（22 条游戏实况 + 23 条实况解说） | 77.3% | 66.7% | **−10.6pp** |

**根因清楚了：各工作表的标注口径互相冲突，一套全局提示词不可能同时满足。**

### 于是改成按表选版本

不再追求全局一致，每个表选它自己合适的版本。
关键是**选择本身不能过拟合**——选择在 dev 上做、test 验证、跑 5 个随机种子：

| 工作表 | 5 个种子的选择 |
|---|---|
| 1月快手-暗区突围 | 全部选 v10 ✅ |
| 1月抖音-无畏契约 | 全部选 v10 ✅ |
| 2月抖音-地铁 / 暗区 / dnfm | 全部选 v8 ✅ |

选择完全一致，test **5/5 正收益**（+4/+3/+3/+1/+1）。

**v3：74.22% → 76.68%（+2.47pp）**

> **教训**：在错误密集子集上做 A/B 会高估收益，因为它没有充分代表「当前判对」的样本。
> 子集只能用来快速排除方向，要采纳必须全量重跑。

## 6. 提示词的三次失败

在 v3 上试了三次用提示词修「创意整活」的边界，全部失败：

| 版本 | 改动 | 结果 |
|---|---|---|
| **v9** | 边界反转为「核心看点是不是梗」 | 全局 −14 |
| **v11** | 补「创意剪辑 vs 创意整活」区分 | 创意剪辑召回 1/25 → **2/25**，几乎没动 |
| **v12** | 加「必须有多人互动」硬性前提 | 80.17% → **76.72%**（−16） |

v12 最能说明问题。业务方给的判据非常明确：

> 「整活要有活，单个玩家没有和队友的强互动」
> 「没有互动，击杀集锦」

我把这条写成**最高优先级**的硬性前提。结果是：

| | 业务口径 | 创意整活精确率 | 业务方指出的 26 条 |
|---|---:|---:|---:|
| v11 | 80.17% | 60.6% | 0/16 |
| v12 | 76.72% | **60.4%** | **0/16** |

精确率几乎没变——**模型没有真正执行这条规则，只是输出分布被扰动了**。

此时提示词已经 7780 字符，包含 24 类定义 + 5 组边界说明。
再加一条「最高优先级」并不会让它真的优先执行。

> **结论**：规则层（后处理）比提示词可控。规则是确定性的，不依赖模型是否「听话」。

### 另一个失败：长视频抽帧

观察到判错的直播切片 17/19 是 >120 秒长视频，而代理只取前 120 秒。
假设抽帧覆盖全片能救。

实测：地铁 **50.32% → 47.10%**，直播切片判对率 60% → 53.3%。
抽帧稀释了视频主体信号。

### 让业务方参与判定

B站 的混淆集中在三类（创意整活 / 游戏实况 / 高光剪辑）。
我把 49 条混淆样本做成可离线打开的 HTML 页面：
每条带视频链接、Excel 标签、模型标签、模型判断依据，业务方选「Excel 对 / 模型对 / 两者都通」。

**49 条全部判定后，结果很有信息量**：

| 判断 | 条数 |
|---|---:|
| Excel 对（模型真错） | 26 |
| 两者都通（口径分歧） | 23 |

从 23 条里归纳出 **3 组口径分歧对**（创意整活／游戏实况、创意整活／高光剪辑、游戏实况／高光剪辑），
加入后 **74.57% → 80.17%（+5.6pp）**。

而且业务方在「为什么」里反复写同一句话：

> 「整活要有活，单个玩家没有和队友的强互动」「没有互动，击杀集锦」

这直接解释了 26 条真实错误里的 8 条。虽然做成提示词没成功（见 §6），
但它是目前最清晰的改进线索。

## 9. 剩余 25 条错误：按成因而不是按标签对

最后阶段发现一个重要事实：**25 条错误分布在 25 个不同的混淆方向上**
（基本每个方向只有 1 条）。这意味着再加豁免对每组只能救 1 条，已经没有意义。

但逐条看完后，它们有 4 类清晰成因：

| 成因 | 条数 | 能不能修 |
|---|---:|---|
| 真人出镜盖掉了更贴切的类 | 8 | **可以修**：要求「真人是主要看点」才判 |
| 内容确实横跨两类 | 10 | **需要定口径**：业务方决定「吐槽 vs 攻略」谁优先 |
| 长视频只看了前段 | 3 | 技术限制 |
| 模型判法更符合定义 | 4 | **建议改 Excel** |

代表性案例：

**真人出镜盖掉别的类**
> `玩家故事 → 直播切片`｜三角洲行动 0:36
> 模型依据：*出现真人（手部）出镜，正在进行游戏内的抽奖，伴随激动的实时语音反应*

一只手入镜就触发了直播判定——判定规程里「主播出镜」优先级最高。

**内容横跨两类**（最大一块，10 条，全部集中在信息型内容的内部划分）
> `游戏吐槽 → 游戏攻略`｜三角洲行动 2:09
> 模型依据：*讲解了「非法抱团」判定机制，并提供规避技巧（互相攻击一下、打一枪队友），属于明确的技巧教学*

视频既在吐槽又给了方法。**这个需要业务方定**：吐槽里带技巧，算哪个？

**模型判法更站得住**
> `角色展示 → 游戏宣传`｜蛋仔派对
> 模型依据：*官方发布的动画剧情PV，描述中明确提及「剧情PV」和新角色上线*

标题自己写着「剧情PV」，按 24 类定义就是游戏宣传。建议改 Excel。

## 10. 调试经验

### 结果异常好 → 先查泄漏

```python
leak = [r for r in rows if r["label"] and r["label"] + "：" in r["desc"]]
```

### 整条失败 → 先查标签集路由

`classify.py` 曾用 `endswith("_v8")` 判断标签集。新版本名
（`bili_v11`、`bili_v12`）不匹配任何分支，**静默退回 16 类**，
导致「游戏测评/皮肤展示/游戏吐槽」被判非法标签，整条失败。

第一次修成枚举 `("_v8","_v9","_v10","_v11")`——v12 又漏了。
最终改成正则提版本号，并**打印实际标签集**：

```python
_m = re.search(r"_v(\d+)$", args.prompt_version)
_n = int(_m.group(1)) if _m else 0
labels = LABELS_V8 if _n >= 8 else (LABELS_V6 if _n >= 6 else LABELS)
print(f"提示词 {args.prompt_version}（版本号 {_n}）-> 标签集 {len(labels)} 类")
```

第一次就是靠日志里的 `bili_v12 -> 标签集 16 类` 才定位到的。

### JSON 解析失败 → 可能是被截断

`max_tokens=700` 对较长的「判断依据」不够，约 5% 的响应 JSON 不完整。
提到 1200，并加正则兜底解析截断的 JSON。

### HTML 报告要在浏览器里实测

静态检查不够。用 Playwright 实际渲染后发现过：

- 混淆矩阵最后一列斜排标签超出 viewBox 9px 被裁
- 分标签精确率的标注文字撑出右边距
- 章节编号重复（批量 patch 中途失败导致）

### 批量 patch 要用原子操作

用 bash heredoc + Python 脚本做多处 `str.replace`，中途一个 `assert` 失败
会导致**整批都没写盘**，但脚本可能已打印部分成功信息。
多次因此丢改动。改用每次替换独立、失败明确报错的方式。
